# 词面最近邻基线：注入材料的可分性检查（2026-10-22）

**结论：** 两批注入材料上，一个不设任何阈值的词面最近邻，在条号类 16 条和款级 31 条上都与规则持平，或多检出 1–2 条，对照均为 0 误报。所以「规则 30 对裁判 1」「规则 14 对 Qwen2.5-72B 4」这类差距，说明的是原提示下的通用裁判基本不核条号或款号，而规则核；不说明规则在语义上判断得更好。

离线、确定性计算，没有发任何模型请求，不参与 Quality Gate，没改规则文件和任何已有归档。

## 为什么做

两次规则对裁判的比较里，规则都明显领先：

- 款项定位 66 条：31 条款级错误，规则检出 30 条，两个裁判原提示下各检出 1 条（[款项定位运行](../20261021-pinpoint-run/README.md)）；
- 正式运行 42 条：条号类 16 条，规则检出 14 条（[正式运行](../20261021-formal/README.md)）。

这里要回答的问题是：这些材料在词面上是不是本来就分得开？如果一个不设任何参数的最近邻就能做到同样甚至更好，规则领先说明的就是「核不核条号或款号」，而不是规则的判断更强。

**材料构造。** 款项定位材料的 35 条错误，去掉条号引用后，都与同一底稿的某条对照逐字相同：只改了引用，内容一字未动。正式运行材料是「每条注入只做一处逐字替换」（见 [法条结构核对](../README.md)「注入实验」一节）。

## 基线定义

脚本是 [`lexical_baseline.py`](lexical_baseline.py)，**看过规则与裁判结果之后才编写**，只能当作可分性检查，不是另一种可以对外宣传的方法。

逐条判定，只看陈述里的第一个条号引用：

1. 没有条号引用：不标记。
2. 所引条/款/项不在节选中：标记（存在性）。
3. 否则，在所引层级的同级单元之间比较规则文件自带的 `_coverage`（陈述去掉条号后的字符二元组，被该单元原文覆盖的比例）。别的单元覆盖率严格高于所引单元，即标记。
   - 不设最小覆盖率，不设差值，不用「前款」交叉引用豁免。
   - 这三项规则都有（`ATTRIBUTION_MIN=0.6`、`ATTRIBUTION_GAP=0.25`、`_mentions` 豁免）。

**余量** = 所引单元覆盖率 − 其余同级单元最高覆盖率。负数表示内容更像别处。

脚本运行时会核对：输入的 `package.json`、法规节选和 `rules.json` 与各自归档的 `SHA256SUMS.txt` 一致，规则结果的 `checkerSha256` 与当前 `statute_check.py` 一致。任何一项不符即停止。

## 结果：款项定位材料（`20261021-pinpoint-run`，66 条）

10-22 [信息对等运行](../20261022-equalinfo/README.md)用的是同一批材料：逐条的 `id`、类型、陈述、预期全部相同，节选哈希相同（脚本输出的 `sameMaterial` 字段）。下表同样适用于那次运行。

| 类型 | 条数 | 规则 | 基线 | 余量范围 |
|---|---:|---:|---:|---|
| 同条存在的另一款 | 18 | 17 | 18 | −0.9231 ～ −0.25 |
| 不存在的款 | 13 | 13 | 13 | （存在性，无余量） |
| **款级错误合计** | **31** | **30** | **31** | |
| 同款存在的另一项 | 3 | 0 | 3 | −0.3333 ～ −0.1111 |
| 不存在的项 | 1 | 1 | 1 | （存在性） |
| 原陈述对照 | 14 | 0 | 0 | +0.1905 ～ +0.7692（7 条无条号引用） |
| 正确款项定位对照 | 13 | 0 | 0 | +0.1111 ～ +1.0 |
| 省略款号对照 | 4 | 0 | 0 | +0.5294 ～ +0.7115 |
| **支持对照合计（误报）** | **31** | **0** | **0** | |

- 只有基线检出的款级错误是 `paragraph_existing-S27-P1`。规则漏它，是因为最接近的第十九条第二款原文自己写了「前款」，触发交叉引用豁免（`statute_check.py:266-268`）。基线不用豁免，所以检出。在这批材料上，这条豁免少检出 1 条；因为基线在对照上也是 0 误报，豁免在这里没有拦下任何误报。
- **项级 3/3 不能当作可分的证据。**
  - 这 3 条（S26）的最佳项覆盖率只有 16/45，余量只有 −0.11 ～ −0.33。
  - 同一陈述引对项时，余量是 +0.1111，就是「正确款项定位对照」的最小值。两者只差在引的是哪一项。
  - 基线能分开，仅仅因为它不设最低覆盖率。
  - 按原规则阈值做的项级比较，仍是 0/3（[事后补查](../20261022-posthoc-locate/README.md)）。
- 款级的余量有实际间隔：错误一侧都 ≤ −0.25，有条号引用的对照一侧都 ≥ +0.1111。

## 结果：正式运行材料（`20261021-formal`，42 条）

| 类型 | 条数 | 规则 | 基线 |
|---|---:|---:|---:|
| 改为节选中的另一条 | 7 | 6 | 7 |
| 改为节选中没有的条 | 7 | 7 | 7 |
| 加一个错的款号 | 2 | 1 | 2 |
| **条号类合计** | **16** | **14** | **16** |
| 原陈述对照 | 11 | 0 | 0 |
| 加一个正确的款号（对照） | 2 | 0 | 0 |
| **对照合计（误报）** | **13** | **0** | **0** |
| 改数额 / 改单位 / 改情态词 / 改极性 | 4 / 2 / 5 / 2 | 4 / 2 / 4 / 0 | 0 / 0 / 0 / 0 |

- 只有基线检出的有两条：
  - `PS-S27`：同样是「前款」豁免。
  - `AS-S32`：「不适用第四条关于投保存款保险的要求」。正式运行的说明认为，条号在这里是「不适用」的对象，不是内容出处。基线不理解这层关系，只看出内容更像别的条。在这批材料上，这恰好标对了。
- 【推断】在真实回答里，同样的写法引对了，基线也可能误报。这批对照里没有这类陈述，测不出来。
- 内容类注入（数额、单位、情态词、极性）不改引用，基线按设计不针对，检出 0 条。这一行只说明基线只看引用，不作比较。

## 这说明什么，不说明什么

- 【事实】两批材料上，不设阈值的词面最近邻在条号类 16 条和款级 31 条上都与规则持平或多 1–2 条，对照都是 0 误报。
- 【推断】所以规则对裁判的差距，说明的是原提示下的通用裁判基本不核条号或款号，而规则核。不说明规则在语义上判断得更好。
  - [补标签对照](../20261022-labeled/README.md)给节选的每一款补上标签后，DeepSeek 的款级检出从 3/31 升到 23/31，Qwen2.5-72B 仍是 2/31。
- 【推断】规则相对这个基线多出来的，是阈值和交叉引用豁免。这两样在本批材料上都没有起作用：没有拦下误报，豁免反而少检出 1 条。它们是否值得，要看真实回答或改写材料。
- 不说明的：
  - 基线在真实回答或改写过内容的陈述上会怎样，没有检验；
  - 基线是事后写的，在同一批材料上检验，没有独立样本；
  - 材料共用底稿，不给区间，只报条数。

## 文件与离线复算

- `lexical_baseline.py`：脚本。
- `analysis/`：输出，包括 `pinpoint.json`、`formal.json` 和 `SHA256SUMS.txt`。逐条记录所引单元、各同级单元覆盖率、余量、基线与规则的判定、规则 error code。
- `analysis-replay/`：第二次运行，用来逐字节比对。两次输出逐字节一致。
- `analysis.stdout.txt`、`analysis-replay.stdout.txt`：两次运行的终端输出。
- 顶层 `SHA256SUMS.txt` 覆盖本目录全部文件。

**归档前的位置。** 脚本最初在 `work/` 下编写和运行。放进本目录时只改了一处：定位仓库根目录的层级，从 `parents[3]` 改为 `parents[4]`。随后在本目录重新运行两次。输出除 `code.script`（脚本自身哈希）外，与 `work/` 下的输出逐字节相同。

复算（不发请求，输出目录必须不存在或为空）：
