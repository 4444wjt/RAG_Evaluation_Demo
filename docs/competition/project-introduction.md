# 鉴真全域 VeriScope AI 作品介绍

> 逐句核对与质量门禁平台

材料日期（PDF 导出）：2026-10-13；证据运行日期：2026-10-05。已完成工作与本轮实验的状态分别说明。

## 一、项目背景

AI 应用上线前，「回答是否可信」的判断往往停在一个平均分或肉眼抽查，既难以解释错误出现在哪一句，也难以据此判断是否达到放行要求。缺少的是**能逐句回查的依据**。

鉴真全域 VeriScope AI 面向 RAG 问答应用：把模型回答拆成逐句，每一句对照检索原文核对是否有依据，再由质量门禁（Quality Gate）按阈值决定这批回答能否放行。题集、检索上下文、模型回答、逐句判定、多模型指标、门禁记录与人工核验汇集到中文工作台，把「回答是否可信」变成一条可逐条回查的结论：

> 题集 → 逐句核对 → 门禁 → 报告 → 人工核验

## 二、创新点

本项目**不自研指标**：指标计算复用 Ragas，工作集中在指标层之上的三层——逐句证据、门禁裁决、人工核验存档，三者绑定在同一份冻结快照（SHA-256）上，可逐条回查。

| 层 | 内容 |
|---|---|
| 自研 | 逐句判定与证据定位；质量门禁裁决（保留真实 FAIL）；人工核验存档（人工意见与机器判定并列、互不覆盖）；中文陈述兼容层 `zh-sentence-v1` |
| 复用 | 指标计算 Ragas 0.1.21；检索与模型调用 LangChain、Chroma、OpenAI-compatible 接口；界面 React、ECharts；部署 Docker Compose（[一键部署](../../deploy/README.md)） |

| 现有方案 | 侧重 | 本项目与之的差异 |
|---|---|---|
| Ragas | 指标计算（忠实度、上下文精度等） | 本项目**以 Ragas 为指标层**，在其上补逐句证据、门禁裁决与人工核验存档 |
| DeepEval | pytest 式断言，指标可设阈值，在 CI 中判定通过与否 | 阈值卡口不是本项目独有；差异在于门禁结论旁并列给出逐句核对证据，可回查到检索原文，并与人工核验分歧放在一起对照（逐句证据不参与门禁计算，门禁由正向忠实度与正向上下文精度决定）；面向中文陈述做了兼容 |
| TruLens | 运行时追踪与可观测（instrumentation） | 本项目聚焦**上线前的固定题集核对**，结论随冻结快照归档，而非运行时观测 |
| LLM Readiness Harness（2026 学术工作） | 面向 LLM / RAG 应用的 CI 质量门禁，把依据性、检索命中、成本、延迟等合成加权就绪分 | 同为上线前门禁，是最接近的已有工作；本项目的差异在于用冻结证据**检验门禁本身**是否可信（复算、换裁判、证据敏感性、结论确定性） |
| AWS Bedrock 依据检查 | 运行时护栏：给单条回答打「有无原文依据」「是否切题」两个分，低于阈值即拦截 | 它在运行时拦截单条回答；本项目在上线前按固定题集判定是否放行，并保留逐句证据与真实 FAIL |
| Azure 依据检测 | 用专门微调的判断模型标出无依据的句子，可选自动改写 | 它给出单条回答的检测结果；本项目不改写回答，重点是门禁结论可回查、可复算 |
| Google Vertex 依据核查 | 给回答一个 0–1 的支持度，可逐条陈述给出引用 | 逐句核对的思路相近；本项目在其上做门禁裁决，并审计门禁本身 |

以上比较基于各项目公开资料（Ragas、DeepEval、TruLens 核对日期 2026-10-11；其余 2026-10-13），不排除其内部已有类似实现；本项目不声称「业界唯一」。

具体创新点（均有实现）：

1. **逐句断言 + 证据回查**：把回答拆成原子陈述，逐句给出「有依据／事实错误／无依据编造」的原判定，并与对应检索原文并列呈现。
2. **质量门禁（Quality Gate）**：按正向忠实度与正向上下文精度双阈值（默认各 0.8）判定是否放行，并**保留真实 FAIL**、不隐藏。
3. **负向样本的拒答语义区分**：对文档未提及的问题，模型拒答属正确行为；系统按样本类型区分对待，避免把「正确拒答」误读为缺失或无法评估。
4. **人工核验存档**：人工结论与机器原判定**分列保存、互不覆盖**，核验材料绑定冻结快照版本与 SHA-256；存档结构有公开的 JSON Schema，并由测试校验。
5. **门禁可回放、可接入 CI**：已归档的运行可离线重新执行门禁裁决（不调用模型），裁决未通过时以非零退出码结束；门禁已打包为 GitHub Action，其他仓库一步接入，CI 页面以作业摘要和 JUnit 报告显示哪个指标未达标、差多少。指定基线后逐题对比上一次运行：按题重抽样求变化区间，并以同一裁判重判的实测波动为噪声底线，只有「确定退步」才拦截，在抽样与裁判波动范围内的下降只提示。
6. **报告可归档**：输出 CSV / HTML / Excel( XLSX ) / PDF 与图表，便于归档与评审。
7. **门禁可信度四问**：对门禁本身做审计——结论能否复算、换裁判会不会变、裁判是否依据证据、结论有多确定。25 题正式运行中，FAIL 可从逐句判定精确重现；换裁判后三次结论一致；按题重抽的 95% 区间为 55.0%–90.0%，跨过 0.8 门槛，属保守拦截而非确定不达标；固定 6 条陈述、只改变提供给裁判的证据（打乱、移除、改成矛盾），两个裁判 59 / 60 个有效判定全部符合作者确认的预期，另有 1 条解析失败如实保留待人工解释。每一问都可从冻结证据离线复算，见[门禁可信度四问](gate-credibility.md)。门禁代码本身另由性质测试（10 条性质）与变异测试检验：42 个人工改坏的变异中测试抓住 39 个，存活的 3 个均不影响放行结论。工作台「门禁审计」页把这些结果集中展示，数据由冻结证据生成并核对哈希。

## 四、应用场景与实际使用案例

### 应用场景：RAG 应用上线验收

对智能问答、知识库问答等 RAG 应用，在上线前用固定测试集跑一次评测，由质量门禁判定是否放行；未通过时，逐句溯源定位到「哪一句、依据哪段上下文、判定是什么」，便于修复与复评。

**典型用法：上线前接入 CI 作回归门禁**；已归档运行可离线重放门禁，不通过即以非零退出码阻断（见 [quality-gate-example.yml](../../.github/workflows/quality-gate-example.yml)）。

### 实际使用案例（仅引用已有运行证据）

- **案例一：25 题单模型正式运行（证据运行日期 2026-10-05）**
  使用《存款保险条例》节选的固定案例集，正向 Faithfulness **0.7375 低于 0.8**，正向 Context Precision 0.9833 达到 0.8 → 原始 Quality Gate **保留 FAIL**。即：**该次评测被门禁拦下**，且完整回答、contexts、指标、Trace、报告与哈希均已归档，可逐条回查失败原因。
- **案例二：历史金融场景旧 CLI 运行**
  正向上下文精度 **0.7778 低于 0.8** → FAIL；该案例与当前演示快照分开保存。

> 两个案例均为**真实运行**：门禁把未达标的评测挡在发布前，逐句溯源给出具体语句与证据。

### 3. 人工核验（13 条定向记录）

作者于 2026-10-05 逐条检查其中 13 条定向记录，结果为 **一致 3 条、存在分歧 5 条、无法确认 5 条**。

## 六、技术限制与诚实边界

- **self-Judge**：当前后端会将相应被测模型用于 Ragas 评测与 Trace 判定，存在生成与裁判同源的偏差；人工核验有助于暴露分歧，但作者自审不能替代独立复核。已做一次量化对照（2026-10-11）：换用 Qwen2.5-72B 作为独立裁判重判 25 题，门禁结论不变（FAIL）；但逐题 Faithfulness 平均绝对差为 0.095，是原裁判自我重判（0.017）的约 5–6 倍；Trace 标签一致率为 72%，原裁判重判为 92%。分歧集中在原本为空的 Trace，需要人工核查，不能判定哪个裁判正确。
- **阈值未业务校准**：默认 0.8 尚无业务校准证明；PASS 仅说明指定样本达到保存门槛，不代表所有指标优秀或每条回答正确。
- **无鉴权与访问隔离**：当前服务定位为本地评测与展示，缺少生产所需的访问控制；公开演示站为只读，不开放在线评测。
- **同步评测**：真实评测采用同步请求，尚无生产所需的完整长任务管理与进度接口。
- **空 Trace 不等于无幻觉**：空 Trace 或缺失指标不能作为无幻觉证明；逐句判定依赖原始溯源记录，不是额外的独立真实性保证。
- **样本范围**：25 题为单一金融材料的固定场景，部分题目共享法条，**不是跨领域 Benchmark、统计独立样本或总体准确率证明**。
- 历史快照还缺少确切的裁判版本、提示词版本与完整环境记录。
