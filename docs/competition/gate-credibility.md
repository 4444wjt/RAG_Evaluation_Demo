# 门禁可信度四问

质量门禁给出一个 PASS / FAIL。发布决策依赖这个结论，所以门禁本身也需要被检验：结论能不能复算，换个裁判会不会变，裁判是否真的依据证据，结论有多确定。本项目把这四件事作为对门禁的审计，每一问都对应一份可离线复算的证据。

工作台的「门禁审计」页集中展示本文四问与附录的结论，数据由 [`tools/competition/build_audit_fixture.py`](../../tools/competition/build_audit_fixture.py) 从同一批冻结证据生成并核对哈希。

这里不新增指标，也不改门禁规则：四问都在已有门禁之外进行，结果只说明门禁结论的可信程度，不用于改判。下文的数字都来自 [25 题正式运行](evidence/20261005T144504Z-full-39511424/README.md)（2026-10-05，DeepSeek，门禁 FAIL）。

| 问题 | 方法 | 当前结论 | 状态 |
|---|---|---|---|
| ① 门禁结论能不能复算？ | 从逐句判定重算每题得分，再重算门禁 | 20 / 20 道正向题与归档一致，门禁 FAIL 可精确重现 | 已验证 |
| ② 换一个裁判，结论会变吗？ | 原裁判重判作噪声基线，另换不同家族的裁判对照 | 门禁结论三次都是 FAIL；逐题差异明显大于随机波动 | 已验证（一次运行） |
| ③ 证据变了，裁判会跟着变吗？ | 固定陈述，改变提供给裁判的证据 | 两个裁判 59 / 60 个有效判定全部符合预期；1 条解析失败需人工解释 | 已运行一次（6 条定向陈述） |
| ④ 这个 FAIL 有多确定？ | 按题重抽求区间，并比较不同计算口径 | 拦截成立，但 20 题的样本不足以确定低于门槛 | 已验证（事后分析） |

## ① 门禁结论能不能复算？

门禁的正向忠实度由 Ragas Faithfulness 计分：回答被拆成陈述，裁判逐条判断能否由检索原文推出，每题得分 = 判为支持的陈述数 / 陈述总数。这些逐条判定保存在调用日志里。

- 从日志中找出全部 52 句陈述的判定，对应到 20 道正向题。每题的支持比例都与归档的 faithfulness 完全一致，均值 0.7375，低于 0.8，门禁 FAIL。
- 门禁回放脚本用与正式评测相同的 `check_quality_gate` 离线重新裁决，不调用模型；裁决不通过时以非零退出码结束，可直接作为 CI 步骤。

证据：[`scripts/gate_replay.py`](../../scripts/gate_replay.py)、[`tools/competition/build_replay_fixture.py`](../../tools/competition/build_replay_fixture.py)，由 [`tests/test_gate_replay.py`](../../tests/test_gate_replay.py) 与 [`tests/test_replay_fixture.py`](../../tests/test_replay_fixture.py) 校验。

```bash
python scripts/gate_replay.py docs/competition/evidence/20261005T144504Z-full-39511424/api-response.json
```

## ② 换一个裁判，结论会变吗？

正式运行中，被评模型同时充当裁判。对照实验只换裁判、不重新生成回答：原裁判再判一次作为噪声基线，再请不同家族的 Qwen2.5-72B 判一次。

| 裁判 | 正向忠实度 | 正向上下文精度 | 门禁 |
|---|---|---|---|
| 原判定 | 0.7375 | 0.9833 | FAIL |
| 原裁判重判 | 0.7583 | 0.9833 | FAIL |
| 独立裁判 | 0.7233 | 0.9389 | FAIL |

- 门禁结论三次都没变，正向均值只变了约 0.01–0.04。
- 逐题看，独立裁判与原判定的差异约是同裁判重判的 5–6 倍（Faithfulness 平均差 0.095 对 0.017，跨门槛的题 6 对 1）。

边界：只做了一次运行，只换了一个裁判；独立裁判不等于正确裁判，分歧样本仍需人工核查。详见 [独立裁判对照](../judge-comparison.md)。

做法参照：[FACTS Grounding](https://deepmind.google/blog/facts-grounding-a-new-benchmark-for-evaluating-the-factuality-of-large-language-models/) 用多个不同家族的裁判共同判定依据性，以减少单一裁判偏向自家模型的问题；[Reliability without Validity](https://arxiv.org/abs/2606.19544) 指出裁判重复判定一致，不代表判得对。本问的噪声基线只说明原裁判自身稳定，跨家族的差异才反映裁判选择对结论的影响。

## ③ 证据变了，裁判会跟着变吗？

前两问检验的是结果，这一问检验裁判的判断依据：固定已有回答中的一句陈述，只改变提供给裁判的证据，看判定是否随依据合理变化。

| 证据条件 | 预期 |
|---|---|
| 原始证据、原样重复 | 支持；两次判定应一致 |
| 打乱片段顺序 | 支持；信息不变，判定不应改变 |
| 移除支持片段 | 依据不足 |
| 把支持片段改成明确矛盾 | 矛盾 |

取 25 题正式运行中 6 条既有陈述（D03–D08），上述 5 种条件，DeepSeek 与 Qwen2.5-72B 两个裁判，共 60 次请求。30 项实验材料由作者 Kk 于 2026-10-12 逐条确认，付费调用单独授权；每个请求只尝试一次，不重试。运行于 2026-10-12 完成，60 / 60 个请求都有返回，按返回用量估算约 ¥0.13（36,903 token），不是账单。

| 证据条件 | DeepSeek | Qwen2.5-72B |
|---|---|---|
| 原始证据 | 6 / 6 判为支持 | 6 / 6 判为支持 |
| 原样重复 | 6 / 6 判为支持，与原始一致 | 6 / 6 判为支持，与原始一致 |
| 打乱片段顺序 | 6 / 6 判为支持，与原始一致 | 6 / 6 判为支持，与原始一致 |
| 移除支持片段 | 6 / 6 判为依据不足 | 5 / 5 判为依据不足；另 1 条解析失败 |
| 改成明确矛盾 | 6 / 6 判为矛盾 | 6 / 6 判为矛盾 |

- 59 个有效判定全部符合作者确认的预期，两个裁判在可比较的配对上标签完全相同。判为支持或矛盾的 48 条都给出了能在指定片段中逐字找到的引用；判为依据不足的 11 条没有引用，与提示要求一致。
- **需要人工解释的 1 条**：D03 移除支持片段后，Qwen2.5-72B 返回的 JSON 判为「支持」，引用的却是第十九条（偿付情形，不涉及谁交保费），随后又追加了一段说明文字，因此按规则记为解析失败、不计入统计。这是本次唯一一处裁判在依据已被移除时倾向于判为支持的迹象，原始返回保留在运行档案中。

边界：6 条是定向挑选、证据边界清楚的陈述，删除和矛盾都是明确的改动；结果说明两个裁判在这类清晰情形下会随证据变化，不能推出它们在细微或隐含的证据变化下同样可靠，也不能估计总体准确率。D03–D05 三条陈述的支持片段是同一段原文，不是独立样本。

证据：[运行档案](judge-sensitivity/run-20261012/manifest.json)（请求、原始返回、用量与哈希）、[离线分析](judge-sensitivity/analysis-20261012/README.md)、[实验说明](judge-sensitivity/README.md)。由 [`tests/test_judge_sensitivity_archive.py`](../../tests/test_judge_sensitivity_archive.py) 校验档案可离线重算出相同结果。

```bash
python tools/competition/judge_sensitivity.py analyze --run docs/competition/judge-sensitivity/run-20261012 --output <新的分析目录>
```

## ④ 这个 FAIL 有多确定？

门禁把 20 道题的均值与 0.8 比较，但 20 题是小样本，均值本身有波动。以「题」为单位有放回重抽 20000 次（同一题的陈述彼此相关，不能当独立样本），得到均值的 95% 区间：

| 指标 | 点估计 | 95% 区间 | 重抽均值达到门槛的比例 | 解读 |
|---|---|---|---|---|
| 正向忠实度 | 73.8% | 55.0%–90.0% | 27.9% | 证据不足 |
| 正向上下文精度 | 98.3% | 95.4%–100.0% | 100.0% | 确定通过 |

解读规则：区间下限也达到门槛为「确定通过」，区间上限仍低于门槛为「确定不通过」，其余为「证据不足」。证据不足时门禁照常拦截，只有确定通过才放行。

正向忠实度的结论还取决于计算口径：

| 口径 | 正向忠实度 |
|---|---|
| 按题平均，拒答按 0 计（门禁口径） | 73.8% |
| 52 句陈述合并计算（43 / 52） | 82.7%，Wilson 95% 区间 70.3%–90.6% |
| 按题平均，拒答不计（16 题，仅作对照） | 92.2% |

- 这次 FAIL 全部来自正向忠实度；上下文精度确定达标。
- 区间跨过了门槛，所以这次拦截是保守拦截，不是「确定不达标」。对照 ② 也是如此：三次裁判给出的均值 0.72–0.76 都落在这个区间内。
- 换成按陈述合并的口径，点估计会超过 0.8。门禁口径是事先设定的规则，拒答按 0 计也是有意的设计（正向题本应可答），这里只用于说明结论对口径敏感，**不能据此把 FAIL 改判为 PASS**。

边界：这个区间**未考虑裁判本身的误差**，只反映题目抽样带来的波动，把每一条逐句判定都当作正确。裁判判错会让真实区间更宽。后续方向是参照 [ICML 2026：How to Correctly Report LLM-as-a-Judge Evaluations](https://proceedings.mlr.press/v306/lee26bl.html)，用非作者的独立人工标注估计裁判误差，再给出同时考虑两类不确定性的区间（已写入 [路线图](../../ROADMAP.md)）。

证据：[`tools/competition/gate_uncertainty.py`](../../tools/competition/gate_uncertainty.py)，由 [`tests/test_gate_uncertainty.py`](../../tests/test_gate_uncertainty.py) 校验。脚本先核对证据哈希和逐句判定，固定随机种子，结果可重复。

```bash
python tools/competition/gate_uncertainty.py
```

## 附：门禁代码本身对不对

四问审计的是门禁结论；这一节检验的是门禁代码 [`backend/core/gate.py`](../../backend/core/gate.py) 本身。检验只新增测试，门禁代码一行未改。

**性质测试**（[`tests/test_gate_properties.py`](../../tests/test_gate_properties.py)，Hypothesis）：自动生成大量输入，检查对所有输入都应成立的规则。判定规则在测试中独立写出，不调用被测代码；固定随机序列（`derandomize`），结果可复现。

| 性质 | 检查方式 |
|---|---|
| 阈值边界正确 | 分数取恰等于阈值、相差一个最小浮点步长、缺失、NaN 等，裁决与规则一致 |
| 分数只升不降，结论不会从放行变为拦截 | 随机提高分数；反向也检查：阈值调高不会让拦截变成放行 |
| 题目顺序不影响结论 | 打乱逐题顺序，经正式的 `aggregate_model_metrics` 重新汇总，正向均值与裁决不变 |
| 负向样本不影响门禁 | 任意增加负向题、任意给分，正向均值与裁决不变 |
| 其他 | 只看第一个有效模型；单用例告警只打印、不改裁决；日志如实打印均值；不修改输入 |

**变异测试**（mutmut 2.5.1）：逐个「改坏」门禁代码（如把 `<` 改成 `<=`、把 `or` 改成 `and`、把下标 0 改成 1），看门禁相关测试能否发现。跳过只改日志文字的字符串类变异。

| 结果 | 数量 |
|---|---|
| 生成的变异 | 42 |
| 被测试抓住 | 39（92.9%） |
| 存活 | 3 |

存活的 3 个都不影响裁决：两个把日志分隔线 `"=" * 50` 改成 51 个字符；一个把 `warning_flag = False` 改成 `None`，两者真假值相同，属于无法被任何测试区分的等价变异。所有改变放行 / 拦截结论的变异都被抓住。

- 本机运行的原始报告归档于 [`gate-self-check/`](gate-self-check/README.md)，并记录被测 `gate.py` 的 SHA-256；门禁代码改动后，「门禁审计」页的数据生成会拒绝使用这份旧结果。
- CI 中的 [`mutation.yml`](../../.github/workflows/mutation.yml) 在门禁代码或门禁测试变动时于 Linux 上重新运行，结果写入作业摘要。
- 本地复现（Linux 或 WSL；mutmut 2 在 Windows 上恢复文件时会改写换行符，运行后需 `git checkout -- backend/core/gate.py`）：

```bash
mutmut run --paths-to-mutate backend/core/gate.py --disable-mutation-types=string,fstring --runner "python -m pytest -x -q tests/test_backend_gate.py tests/test_gate_properties.py tests/test_gate_replay.py tests/test_backend_pipeline.py"
```

边界：变异得分说明测试能发现这些人工改动，不证明门禁代码没有其他缺陷；变异类型取 mutmut 默认集合（除字符串类）。做法参考 [An Empirical Evaluation of Property-Based Testing in Python](https://doi.org/10.1145/3764068)（OOPSLA 2025）。

## 边界

- 四问都基于同一份单领域、25 题的正式运行，结论不能推广到其他领域或其他题集。
- ④ 是对已有结论的事后分析，只说明确定程度；门禁规则与已记录的 FAIL 保持不变。
- ③ 只运行了一次，每个条件每个裁判只判一次，且只覆盖证据边界清楚的 6 条陈述。
- 这些方法各有先例：按输入变化检验行为借鉴 [CheckList](https://aclanthology.org/2020.acl-main.442/) 与 [RAG 变形测试研究](https://arxiv.org/abs/2607.26843)；小样本不宜套用正态近似，见 [ICML 2025 立场论文](https://icml.cc/virtual/2025/poster/40132)。本项目的工作是把它们组合起来，用于审计一个中文 RAG 质量门禁，并让每一问都能从冻结证据离线复算；不宣称首创。
