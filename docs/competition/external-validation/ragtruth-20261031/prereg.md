## 1. 研究问题

在开发中从未使用过的英文公开数据上，逐句核对对两类回答判 `FAIL` 的比例各是多少：

- RAGTruth 人工标注为无幻觉、且不是固定拒答的回答（M2）；
- 标注含幻觉、且不是固定拒答的回答（M1）。

**只做估计，不设「成立／不成立」阈值。** 本项目没有可作依据的误报容忍线。本批次不跑对照基线，也不登记任何「优于某方法」的比较。

## 2. 输入与判定

### 2.1 字段映射

| task | question | contexts | answer |
|---|---|---|---|
| QA | `source_info['question']` | `[source_info['passages']]`（字符串） | `response` |
| Summary | `prompt[:prompt.index(source_info)].strip()` | `[source_info]` | `response` |
| Data2txt | `prompt.split('Structured data:', 1)[0].strip()` | `[json.dumps(source_info, ensure_ascii=False)]`，不排序、不缩进 | `response` |

- 上述锚点已在固定 commit 的全量数据中核对：Summary 的原文在 `prompt` 中恰好出现一次，Data2txt 的 `Structured data:` 恰好出现一次。找不到锚点或字段类型不符时，`prepare` 报错退出，不做兜底。
- `ground_truth` 传空字符串：RAGTruth 没有参考答案字段，核对提示词会代入该字段。10-13 的 ANAH 运行同样传空。
- `labels` 只用于分组和统计，不进入核对输入。

### 2.2 模型与调用

- 模型：`deepseek-flash`。按 DeepSeek 官方文档发送 `thinking: {"type": "disabled"}`；temperature 0；max_tokens 4096；`stream: false`；socket 超时 180 秒（单次读写的等待上限；服务端持续发空行时，总时长可超过 180 秒）；不重试。
- 设 max_tokens 是为了让单次花费有可证的上限（见 S1）：价目页写明 `deepseek-flash` 最大输出 384K，不设上限时单次输出费用最高约 ¥3。被截断的输出照 trace 原有的解析处理（通常为 `parse_error`），`finish_reason` 为 `length` 的条数单独报告。
- 不沿用 10-13 的请求名 `deepseek-chat`，分三点说明：
  - 事实：10-13 的归档记录请求模型为 `deepseek-chat`，服务端返回的模型名 500 次均为 `deepseek-flash`（`docs/competition/external-validation/summary.json` 第 20–22 行）。
  - 事实：现行价目页已不再列出 `deepseek-chat`；`deepseek-flash` 现在指向 DeepSeek-V4.1-Flash-1017，默认开启思考模式。本批次改用 `deepseek-flash` 并关闭思考。
  - 未核到：10-13 返回的 `deepseek-flash` 与现在的是否为同一权重，归档里没有版本记录。因此本批次的数字不与 10-13 直接比较。
- 适配层直接调用 `https://api.deepseek.com/chat/completions`（地址固定，不跟随重定向），保存每次的原始响应，把正文、返回的 `model`、`finish_reason` 和用量交给 `trace_hallucinations`，核对提示词与解析都不改。原因：项目里的 langchain-openai 0.1.25 会丢掉 `reasoning_content`，用它取回结果就无法检查 S5。
- 非 HTTP 200 的响应、连接失败、超时，以及 HTTP 200 但不是完成响应的（正文不是 JSON 对象，或对象中没有非空的 `choices` 列表），都由 trace 记为 `call_error`。最后一种的来源：
  - 事实：DeepSeek 文档写明，非流式请求等待期间服务端持续返回空行，10 分钟内未开始推理就断开连接。
  - 推断：空行属于响应正文，状态行已先发出，因此可能收到状态 200、正文只有空行的响应。它没有回答内容，不影响结果有效性，不做 S5 检查。
- 发付费调用前先请求免费的 `GET /models`：状态不是 200，或列表里没有 `deepseek-flash`，就中止，不发付费调用。
- 密钥只在 `run` 时从进程环境的 `OPENAI_API_KEY` 读取，不写入任何文件；运行需设置 `VS_ALLOW_PAID=1`。导入 `backend.services` 时，`backend/config.py` 会加载仓库本地的 `.env`（不覆盖已有环境变量），与 10-13 的工具相同。

### 2.3 每条回答的结论

| 结论 | 条件 |
|---|---|
| `FAIL` | `trace_status` 为 `ok` 或 `partial`，且保留下来的陈述里有任一条为 `fact_error` 或 `fabrication` |
| `PASS` | `trace_status` 为 `ok` 或 `partial`，且保留下来的陈述全部为 `supported`（至少一条） |
| `UNVERIFIED` | `trace_status` 为 `call_error`、`parse_error`、`invalid_structure`、`empty_answer`、`model_empty` 或 `filtered_all`；或外层记录状态不是 `ok`（适配层出错或运行中断，没有 trace 结果） |
| `NOT_RUN` | 抽中了，但因停止条件没有发出调用 |

- `filtered_all` 的意思是模型返回了陈述，但全部没通过 `_validate_statements` 的校验，原因有 6 种：`invalid_statement`、`missing_text`、`invalid_verdict`、`missing_evidence_field`、`evidence_not_in_context`、`missing_required_evidence`（`trace.py` 第 155–185 行）。它不是「没有抽出陈述」。
- `partial` 单独计数，并按 §2.4 另报敏感性数字。

### 2.4 指标

| 指标 | 定义 | 性质 |
|---|---|---|
| **M2** 与标注不一致率 | N2 中 `FAIL` ÷（N2 中 `PASS` + `FAIL`） | 主估计 |
| M2 保守值 | N2 中（`FAIL` + `UNVERIFIED` + `NOT_RUN`）÷ N2 抽中数（300） | 与 M2 同时报 |
| M1 | N1 中 `FAIL` ÷（N1 中 `PASS` + `FAIL`） | 描述性 |
| M2-ok | 只看 `trace_status` 为 `ok` 的 N2 回答时的 M2 | 敏感性，描述性 |

- 各指标都报 95% Wilson 区间。分母为 0 的指标（包括按 task 分开的子组）记为 null，不算区间，沿用 `external_validation.py` 中 `_rate` 与 `wilson` 的处理。
- 按 task 分开报。另外分别计数：`UNVERIFIED` 各状态的条数；`NOT_RUN` 条数；`finish_reason` 为 `length` 的条数；被剔除陈述的原因（`rejected_statements.reason`）；`quality` 与 `model` 的分布。
- 叫「与标注不一致率」，不叫「误杀率」：RAGTruth 无标注不等于上下文逐字支持，而核对要求的是后者。

## 3. 样本

### 3.1 合格条件

在抽样前执行，各项排除数按「task × 组」单独记录；每条回答只计入它不满足的第一条（按第 1、2、4 条的顺序）：

1. `split` = `test`；
2. contexts 文本合计 ≥ 200 字符；
3. `quality`（`good` / `incorrect_refusal` / `truncated`）不作排除条件，分开计数；
4. `response` 不含固定拒答句：`'unable to answer based on given passages' in response.lower()` 为真即排除（不区分大小写）。

第 4 条的理由：RAGTruth QA 的生成提示要求无法回答时回复这一固定句（固定 commit 中 989 个 QA `prompt` 全部含此句）。只有这一句的回答没有可核对的事实陈述：核对模型返回空陈述时记为 `model_empty`（不匹配 trace 的中文拒答正则），落入 `UNVERIFIED`，压低 N2 有效数，又不提供关于 FAIL 的信息。按子串判定时，含此句但另有其他内容的回答也会被排除：test 中含此句的 86 条（都在 QA）里，只有这一句的 26 条（去掉首尾空白和句末标点后等于该句，都在 N2），另有其他内容的 60 条（N2 42、N1 18）。仍按子串判定、两类一并排除，理由是规则简单、可复算；代价是结论不覆盖这 60 条（§7）。全量数据中含此句的回答 762 条（区分大小写为 749 条），都在 QA。本条在看到任何核对结果之前确定。

### 3.2 分组与池子

- **N1**：`labels` 非空。包括标了 `implicit_true` 或 `due_to_null` 的 span，因为它们在上下文中同样没有依据。
- **N2**：`labels` 为空。

池子大小由 `prepare` 统计后填写：

| 组 | 合格回答数 | 合格 source 数 | 按 task 的 source 数（QA / Summary / Data2txt） | 第 4 条排除的回答数 |
|---|---:|---:|---|---:|
| N1 | 925 | 371 | 90 / 131 / 150 | 18 |
| N2 | 1,689 | 443 | 150 / 149 / 144 | 68 |

- 按第 1、2 条排除的：两组均无 contexts 不足 200 字符的回答；非 test 的回答共 15,090 条。
- 按 §3.3 第 1 条分配的名额：N2 为 102 / 101 / 97，N1 为 24 / 35 / 41（QA / Summary / Data2txt）。
- 合格池的 `quality`：N2 为 good 1,686、incorrect_refusal 2、truncated 1；N1 全部为 good（925）。
- 合格池 contexts 字符数（最小 / 中位 / 最大）：N2 为 739 / 1,906 / 9,918，N1 为 744 / 2,183 / 9,918。

### 3.3 抽样（N2 = 300，N1 = 100）

1. 两组分别抽，先 N2 后 N1。组内按 task 分层，各层名额按该层合格 source 数的占比分配，用最大余数法：先取整数部分，余数按小数部分从大到小补齐；小数部分相同时，按 QA、Summary、Data2txt 的顺序。
2. 层内先抽 source，再从每个入选 source 的合格回答里随机抽 1 条。组内每个 source 至多 1 条；两组之间允许同一 source 各出 1 条。
3. 全部随机步骤共用一个 `random.Random(20261031)`，依次为：N2、N1、运行顺序、试跑。每层先 `rng.sample(sorted(source_ids), 名额)`，再对排序后的入选 source 逐个 `rng.choice(sorted(合格回答 id))`。排序一律按字符串字典序。
4. `model` 不预先分层，事后报分布。
5. 某层合格 source 少于名额时，`prepare` 报错，不补抽，也不跨层挪用名额，在冻结前改本登记。
6. 运行顺序：400 条按「N2 抽样顺序 + N1 抽样顺序」排列后，用同一随机数生成器打乱。
7. 试跑 5 条：从 `split` = `train`、满足 §3.1 第 2、4 条、且 `source_id` 不在正式样本中的回答里，按 `id` 排序后打乱；依次取第一条 QA、第一条 Summary、第一条 Data2txt，再按顺序取 2 条（任意 task）。试跑不计入结果，单独归档。
8. 样本包里不写生成时间等随运行变化的字段，按 LF 换行写入：同一 commit、同一数据重跑 `prepare`，应得到逐字节相同的样本包。

## 4. 停止条件

出现任一情况就停止，并如实报告。S1–S3 停止后，已完成的照常分析，没发出的记为 `NOT_RUN`，不补跑，能否报告按 §5 判定。S5 触发则本批次作废。

| # | 条件 | 处理 |
|---|---|---|
| S1 | 预算。单次调用花费的可证上界取 R_max = 1,048,576 × ¥2 / 百万 + 4,096 × ¥8 / 百万 = ¥2.12992：价目页写明上下文长度 1M（这里按 2^20 取大），输入不会超过它；输出不超过 max_tokens。每次调用前，「已结算 + R_max」超过 §6 硬上限时停止，不发这次调用（等于时允许）。正式运行的「已结算」包含试跑合计。调用后按 usage 的输入、输出 token 数结算，输入一律按缓存未命中价；usage 缺失或不完整的（包括超时、连接失败、非 200 响应、正文只有空行的 200 响应）按 R_max 结算 | 停止 |
| S2 | 正式运行从第 50 次调用起，每次调用后检查：累计失败数 ÷ 累计调用数 > 10%。失败指 `call_error`、`parse_error`、`invalid_structure`，以及外层记录状态不是 `ok`。试跑不计入 | 停止，报告失败分布（错误类型、是否集中在某类样本） |
| S3 | 正式运行中连续 20 次 `call_error`。与 S2 不同，这里只计调用失败，不计解析失败和结构无效：连续解析失败更可能来自样本形态（例如某类任务的回答格式），不是环境故障；按环境故障停机，会把样本问题误判为故障。解析类失败由 S2 的比例条件处理 | 停止，按环境或凭证问题排查 |
| S5 | 只检查完成响应（HTTP 200，正文是含非空 `choices` 列表的 JSON 对象；其他 HTTP 200 响应按 §2.2 记 `call_error`）。以下任一：① 以试跑中第一个完成响应的 `model` 字段为基准，这个字段缺失或为空即触发；之后任一完成响应的 `model` 与基准不同，缺失或为空也算；② 任一响应 `choices[0].message` 里 `reasoning_content`、`reasoning` 或 `thinking` 字段存在且非空；③ 正文匹配 `</?(think\|thinking\|analysis\|reasoning)>`（不区分大小写）；④ 请求体中除 `messages` 外的任一字段与 `authorization.json` 登记的不一致 | 立即停止，本批次作废，另开 amendment 重跑 |

试跑的 5 条同样按 S5 检查。试跑结束时必须已有非空的 `model` 基准；没有基准（例如 5 次都没有完成响应），或试跑触发 S5，正式运行都不得开始，另开 amendment。

运行中断的处理：每次调用前先写一条预留台账并落盘。收到响应后，先在内存中完成分类与 S5 判定，写结算（含状态码、S5 判定结果和原始字节的 SHA-256），再保存原始字节，因此不会出现已保存却未判定的响应。续跑时，只有预留、没有结算的那次按 R_max 结算，该条记为外层状态 `interrupted`（`UNVERIFIED`），不重发；已结算但没有记录的，按结算行补记为 `interrupted`，结算行带有 S5 判定的照样作废本批次。同一运行目录加锁，不允许并发运行。

S4 是跑完后的解释条件，不是停止条件，见 §5。

## 5. 结果措辞

**S4（跑完后判定）：** N1 的有效数（`PASS` + `FAIL`）为 0，或 M1 < 5%，即为触发。触发时 M2 不作解读，数字只留在归档里。

| 情形 | 允许写的 |
|---|---|
| N2 有效数（`PASS` + `FAIL`）≥ 250，且未触发 S4 | 「RAGTruth 测试集按登记抽取 300 条无标注、非固定拒答的回答，逐句核对判 FAIL 的比例为 x%（95% CI a–b，有效 n）；未核验 k 条、未执行 m 条，全部计为 FAIL 时为 y%（95% CI a′–b′）」，并附 M1、按 task 的数字和 §2.4 的描述性数字 |
| N2 有效数 < 250 | 「本次未取得可报告的结论」，不引用 M2 数字 |
| 触发 S4，且 N1 有效数为 0 | 「N1 没有有效结果，本次 M2 不作解读」 |
| 触发 S4，且 M1 < 5% | 「核对在该数据上几乎不触发，本次 M2 不作解读」 |
| 触发 S5 | 本批次作废，不引用任何数字 |

- 不写「低」「高」「优于」「达到」一类评价词。
- 不与其他系统或数据集的数字做比较；分别报告时注明单位是「整条回答」。
- 结果不利也照写。

## 6. 费用

| 项 | 值 |
|---|---|
| 调用次数 | 正式 400 次，试跑 5 次。每条回答 1 次核对调用，不生成新回答 |
| 计价 | `deepseek-flash` 高峰价：输入（缓存未命中）¥2、输出 ¥8 / 百万 token，保守取值 |
| 单次最大花费 | R_max = ¥2.12992（见 S1）。因此累计结算超过 ¥12.87008（硬上限 − R_max）后，不再发调用 |
| 保守估算 | `estimate()` 按提示字数（英文字符按 1 token 计）加 800 token 输出估算，用于计划，不是上界。按 `prepare` 的结果：405 次调用，输入约 1,580,945 token、输出 324,000 token，约 ¥5.75 |
| 硬上限 | ¥15（试跑与正式运行合计），代码中为常量。`prepare` 算出的保守估算若超过 ¥12.87008（硬上限 − R_max），冻结前改本登记，不在运行中抬高 |
| 试跑后 | 「试跑合计 + 400 × 试跑中按 usage 结算的调用的平均费用」超过 ¥12.87008，或试跑没有按 usage 结算的调用：不授权正式运行，另开 amendment，只改预算或样本量 |

- 没有 usage 的调用每次按 ¥2.12992 计入。这类调用出现几次，正式运行就可能提前停止（没发出的记 `NOT_RUN`）。这是保证硬上限的代价。
- 参考：10-13 共 500 次调用，按返回用量估算 ¥2.68，平均每次输入 2,295 token、输出 96 token。这是 300 次 ANAH 单句核对、100 次 RGB 作答、100 次 RGB 核对三类调用的平均值，只作量级参考；本批次核对整条回答，输出会更长，以试跑实测为准。

## 7. 能说什么、不能说什么

**能说：** §5 允许的句子。这是在开发中未使用过的英文公开数据上，按跑前登记得到的结果。

**不能说：**

- 不能说成质量门禁的效果。门禁按整批正向忠实度与上下文精度的均值判定，与逐句核对是两次独立的调用。
- 不能说误报低，或优于某方法：本批次没有阈值，也没有对照基线。

他人复算的步骤是：按固定 commit 下载数据，用同一代码 `prepare` 重建样本包并比对哈希，再对公开的逐条记录运行 `analyze`。
