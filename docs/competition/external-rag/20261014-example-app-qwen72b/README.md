# 外部 RAG 端到端实测：本机示例应用（2026-10-14）

**结论：** 端到端接入链路完整跑通，25 题全部评测完成，门禁 **FAIL**。正向忠实度 `0.6686`，95% 区间 `0.515–0.8117`，跨过阈值 `0.8`，结论确定性为「证据不足」。

这次运行验证的是**接入链路**，不是某个应用的质量。被测应用是本仓库自写的示例程序，不是第三方系统。门禁分数还受到裁判问题的影响（见下文「裁判的两种核对互相矛盾」）。

## 被测应用

[`examples/external_rag_app/app.py`](../../../../examples/external_rag_app/app.py)（SHA-256 `adfffa22…f8a`，本次运行时的版本）：

- 只用 Python 标准库，按 `veriscope.e2e.v1` 契约接收题号和问题。
- 自己检索：把《存款保险条例》节选按「第 X 条」切分，按字符二元组重合度取前 3 段。平台的检索是向量检索，两者不同。
- 自己生成：调用 DeepSeek（`deepseek-chat`，实际返回 `deepseek-flash`），温度 0。提示词由应用自己写，资料不足时固定回答「资料中没有足够信息回答这个问题。」，并自报 `status: refused`。
- 返回实际交给生成模型的 3 段资料，附条号和检索分数。

平台只发送题号和问题，不发送参考答案、平台检索结果或题目类别。

- 裁判为 `Qwen/Qwen2.5-72B-Instruct`（硅基流动），五项指标与逐句核对都由它完成，生成方与裁判方不是同一家模型。
- 门禁代码与阈值未改：`sources/backend/core/gate.py` 的哈希为 `89d98d3a…`，与仓库一致。

### 应用的作答行为

- **错误前提题 F01–F05：5 道全部依据资料纠正**，没有拒答。比如 F04 指出条文是「7 个工作日」而不是「7 个自然日」，并引用了第十九条原文。
- **资料没有答案的 N01–N05：5 道全部拒答**，应用自报 `refused`。
- 15 道正常题全部作答。逐句核对完成的 32 条陈述中，没有判为事实错误或编造的。

### 发现 1：裁判的两种核对互相矛盾

拉低门禁分数的 11 道正向题里，逐句核对的陈述**全部**判为有依据，忠实度却只有 `0`–`0.75`。最明显的两题：

- **D05**：回答逐条复述第四条的三类除外存款，逐句核对 3 条陈述全部有依据，证据是第四条原文；忠实度却是 `0`。
- **D09**：回答复述第十条的保费计算方式，逐句核对判为有依据；忠实度也是 `0`。

两个分数都出自同一个裁判模型，只是 Ragas 忠实度与逐句核对的提示词和拆句方式不同。门禁用的是忠实度，所以这次 FAIL 里至少有一部分来自裁判的问题，不能直接算作应用的问题。原因未核实。同日的 [独立裁判复核](../../evidence/20261014T125415Z-full-a5002d4f/README.md) 中，同一裁判也出现了同样的情况（D10、F02 等）。

### 发现 2：拒答识别没有认出应用的拒答句

- 应用对 N01–N05 都自报 `refused`，但平台按固定短语识别拒答（`backend/core/attribution.is_refusal`），没有认出「资料中没有足够信息回答这个问题」。
- 因此报告里的拒答准确率是 `0.0`，逐题记录标为「不一致（保留两者，不改判）」。
- 这与契约的约定一致：应用声明与平台识别分别保留，不改判。拒答准确率不参与门禁，门禁结论不受影响。
- 但这说明，按短语识别拒答对外部应用不可靠。本次没有修改识别规则；改动需要单独提出。

### 逐句核对覆盖

- 25 题中，D06、D07、D08、N02 共 4 题因供应商限流（RateLimitError）核对失败；N03 的陈述被证据校验全部过滤；F01、F03 部分完成。
- 逐句核对不参与门禁。

## 不能说明什么

- 示例应用是为验证链路自写的，不代表任何真实部署的 RAG 系统。
- 检索方式与平台不同，不能和平台自己检索的运行比较高低。
- 资料只是应用的自报，平台没有验证应用内部是否真的用这 3 段生成回答。
- 只跑了一次，只用了一个裁判；裁判自身的矛盾见发现 1。
